- 2026-07-27(X 宣伝動画、ユーザー指摘「3041 は僕個人の数字でほかの人にとっては意味ないのでどういう位置づけか教えてもらえますか？」): プロモのカウンターに、ブロックが崩れるたびの中間値(3,041 / 1,204)を**読める速度で**出す設計にしていた。1 コマ目の草で「これはあなたの 1 年だ」と自分ごとにさせておきながら、直後に読める他人の実数を置くと、視聴者は「これは誰の数字だ」と我に返り、作ったばかりの自分ごと感を自分の手で壊す。**ルール: 視聴者に固有値を見せるときは、数字ごとに「それは誰のもので、読めることで何が伝わるか」を問う。伝えたいのが量の *変化* (減っている)なら、値は読ませないほうが強い — 読める数字は意味の解釈を要求するが、読めない数字は運動だけを伝える。実データの両端(開始値と着地点)だけを読ませ、途中は読み取れない速度で回す。** 一般化すると、**「実データだから正しい」と「その数字が視聴者にとって意味を持つ」は別の話**で、前者だけを根拠に画面へ置いていた。

- 2026-07-25(セッション12、本番だけ Lighthouse が赤い件): `pnpm lh`(dist)が 100/100/100/100 なのに本番が performance 76 だった。原因は「本番が遅い」ではなく **計測条件のほうが劣化を検出できない形をしていた**こと — dist は localhost 配信で RTT ≒ 0 / TTFB ≒ 20ms なので、**クリティカルパスの往復が何回あっても FCP がほとんど動かない**。そのため「First Paint が module JS の実行を待っている」(`#app` が空でシェルを JS が組み立てていた)という構造的な問題が、2 セッション連続で 100 点のまま通り抜けた。**ルール: 「ローカルでは緑、本番だけ赤」を見たら、まず本番の数字ではなく *ローカル計測が何を測れていないか* を疑う。ラボの計測環境は、守りたい性質(ここではクリティカルパスの往復回数)が壊れたときに実際に赤くなることを一度確かめる — 落ちないゲートは通っていても意味がない。** 対策として dist と同じ成果物を TTFB 170ms のサーバから配信する `slow` ターゲットを足した。また、**監査名に引きずられない**こと: `render-blocking-resources` が 1 件残っていたので 2 セッションぶんそこを掘っていたが、FCP を止めていたのは render-blocking ではなく「HTML に中身が無い」ことだった。指標(FCP)の定義から要素(LCP 要素 `p.subtitle`)がどこで生まれるかを追うほうが速い。

- 2026-07-25(セッション8、ユーザー指摘「スマホだと全然できない」): 「375px でレイアウトが破綻しない」ことをモバイル対応と呼んでいた。実際にはレイアウト以前に**操作系が成立していなかった** — 盤面上のドラッグはボールとパドルを指で覆い、`pointerdown` が即発射で狙えない。マウス前提の入力をそのままタッチに流用しただけだった。**ルール: 入力を持つ画面のレスポンシブ確認は「見た目が崩れないか」ではなく「その入力デバイスでクリアできるか」で判定する。ポインタ操作は `pointerType` ごとに設計が別物になり得る(タッチは指が画面を隠す・ホバーが無い・押下と決定を分けられない)。** さらにレビューで、タッチ操作面を新設しても**旧操作面を残したままだと元のバグに戻れる**(数 px 外すと盤面に落ちる)、**マルチタッチでは `pointerId` を見ないと2本目の指がドラッグを奪う**という2点を指摘された。タッチ実装は必ず (1) 旧操作面の無効化 (2) pointerId の所有権 (3) `pointercancel` の3点をセットで確認する。

- 2026-07-25(セッション8 再レビュー H-A): 「タッチはレールが受けるので盤面は無視」という修正で、**CSS(レールの表示条件)と JS(盤面の無視条件)に別々の判定を書いた**。`@media (pointer: coarse)` は*主*入力しか見ないため、タッチスクリーン付きノート PC では前者が偽・後者が真になり、レールも出ないのに盤面もタッチを拒む「操作不能」を新たに作っていた。**ルール: 同じ1つの事実(この端末はレールを使うか)を 2 箇所に書かない。CSS が決めるなら JS は CSS の結果(要素の実寸)を読む。** さらに一般則として、**既存の入力経路を塞ぐ変更は、代わりの経路が必ず存在することを同じ条件式で保証してからにする**(塞ぐ側と与える側が別条件なら、その差集合が死ぬ)。加えて、`pointer` / `any-pointer` / `hover` の違いは実機が無くても仕様を読めば分かる — 「ハイブリッド機でも実害なし」と Assumption に VERIFIED で書いたのは、仕様を確認せず自分の期待を書いていた。

- 2026-07-26(セッション14、ユーザー指摘「in app ブラウザーだと <560px 制限に引っかかって非表示ですか？」): クリア時のひとことが 375px で「ちょうど収まる」と判定して実装を進め、実際には溢れていた。原因は**溢れ判定に `scrollHeight` を使ったこと** — `display:flex` + `justify-content: center` のコンテナは、はみ出した分を上下に等分に押し出すが、スクロール原点より上の分は `scrollHeight` に現れない。そのため「128/128 でぴったり」という嘘の緑を 2 回読んで、次に「では狭幅は全部あきらめる」と `<560px` 一律非表示という**過剰に広い線引き**まで引いた。ユーザーの実機(幅 ~450px)には 29px も余っていた。**ルール: flex コンテナの溢れは `scrollHeight` で測らない。子要素の高さ + gap + padding を足して `clientHeight` と比べる(overflow が hidden/auto でも、center 寄せでも正しい)。** そしてもう一段: **「入らない」を理由に機能を落とすときは、入らない境界を実測で特定してからにする。** 既存のブレークポイント(ここでは 560px)をそのまま流用すると、実際の制約(盤面高 =(幅−34)×0.375 で決まる)とずれた範囲まで巻き添えにする。今回の実際の境界は 375px 前後で、余裕を見て 390px 未満だけ非表示にした。

- 2026-07-26(セッション14 続き、ユーザー指摘「スマホだと確実に狭くてメッセージ見えない仕様であってますか？」): 上の測り直しのあとも、まだ「390px 未満は非表示」という機能の切り落としを残していた。理由は**「オーバーレイ = 盤面」という自分で書いた制約を、動かせない前提として扱った**こと。実際にはラウンド終了後の盤面下(パドルレール)は無効化済みで誰も触らない領域であり、`bottom: auto` + `min-height: 100%` の 2 行でパネルを下へ伸ばせば、全幅で出せたうえに 0.1px 単位の高さ調整も丸ごと不要になった。**ルール: 「入らないから出さない」を選ぶ前に、入れ物のほうが動かせないかを必ず一度疑う。とくに自分が同じ設計ドキュメントに書いた制約は、外部要件ではなく過去の自分の判断なので、コストと引き換えに改訂できる。**制約の出どころ(仕様 / 物理 / 過去の自分)を区別せずに一律「守るもの」と扱うと、ユーザーに見える機能のほうを削ってしまう。

- 2026-07-26(セッション14、デザインレビュー後の共有物対応): 煽り文を OGP カードと保存画像に載せたところ、**どちらもフォントが無言で壊れた** — OGP は全部豆腐、保存画像は DotGothic16 のはずが丸ゴシック。原因は共通で、両方とも表示フォントを `text=` サブセットで取得しており(パフォーマンス対策)、**サブセットに無い字はエラーを出さずに代替書体で描かれる**こと。ユニットテストは緑、HTTP は 200、例外もゼロ。実物の PNG を目で見るまで誰も気づけない。**ルール: フォントをサブセット取得している系で表示文言を足したら、必ず (1) サブセット定義に文字を足し、(2) 実物をレンダリングして目で確認する。**さらに再発を防ぐため、文言の一次データ(`CLEAR_MESSAGES`)を公開してサブセットをそこから組み立て、取りこぼしを検出するテストを両方に置いた — 「2 か所に同じ文字列を書く」構造そのものが原因なので、片方を導出にするまでは直っていない。
  副次的な学び: **CJK の書体判定に `measureText` の幅を使ってはいけない**。全角字はどの書体でも 1em なので、フォールバックしていても幅は一致する。実際これで一度「フォールバックしていない」と誤判定した。判定するならピクセルを比較する(小さい canvas に 1 字描いて ImageData を比べる)。

- 2026-08-01(セッション18、自己修正・ストアのショップアイコンを消した): ローカライズ版スクリーンショットを削除するループで、対象セクションを「ラベル要素から祖先を上へたどり、最初に画像ボックスを含んだ要素」として毎回引き直していた。対象が 0 枚になった瞬間この探索が**画像アセット全体(7 枚)にフォールバック**し、その先頭にあったショップアイコンに削除を撃った。ループの終了条件を「対象セクションが空か」ではなく「探索が何かを見つけたか」に依存させていたのが原因。**ルール: 破壊的な操作をループで回すときは、対象コンテナを *ループの外で 1 回だけ* 解決して固定する。毎周回で探索し直す設計は、対象が消えた瞬間に別のものを掴む。** 併せて、削除のような不可逆操作は 1 件ごとに「消したのは意図した対象か」を ID/ラベルで照合してから次に進む(今回 `aria-label` に「画像を削除 ショップ アイコン」と書いてあり、照合していれば即座に止まれた)。
