# Lessons

- 2026-07-25(セッション8、ユーザー指摘「スマホだと全然できない」): 「375px でレイアウトが破綻しない」ことをモバイル対応と呼んでいた。実際にはレイアウト以前に**操作系が成立していなかった** — 盤面上のドラッグはボールとパドルを指で覆い、`pointerdown` が即発射で狙えない。マウス前提の入力をそのままタッチに流用しただけだった。**ルール: 入力を持つ画面のレスポンシブ確認は「見た目が崩れないか」ではなく「その入力デバイスでクリアできるか」で判定する。ポインタ操作は `pointerType` ごとに設計が別物になり得る(タッチは指が画面を隠す・ホバーが無い・押下と決定を分けられない)。** さらにレビューで、タッチ操作面を新設しても**旧操作面を残したままだと元のバグに戻れる**(数 px 外すと盤面に落ちる)、**マルチタッチでは `pointerId` を見ないと2本目の指がドラッグを奪う**という2点を指摘された。タッチ実装は必ず (1) 旧操作面の無効化 (2) pointerId の所有権 (3) `pointercancel` の3点をセットで確認する。

- 2026-07-25(セッション8 再レビュー H-A): 「タッチはレールが受けるので盤面は無視」という修正で、**CSS(レールの表示条件)と JS(盤面の無視条件)に別々の判定を書いた**。`@media (pointer: coarse)` は*主*入力しか見ないため、タッチスクリーン付きノート PC では前者が偽・後者が真になり、レールも出ないのに盤面もタッチを拒む「操作不能」を新たに作っていた。**ルール: 同じ1つの事実(この端末はレールを使うか)を 2 箇所に書かない。CSS が決めるなら JS は CSS の結果(要素の実寸)を読む。** さらに一般則として、**既存の入力経路を塞ぐ変更は、代わりの経路が必ず存在することを同じ条件式で保証してからにする**(塞ぐ側と与える側が別条件なら、その差集合が死ぬ)。加えて、`pointer` / `any-pointer` / `hover` の違いは実機が無くても仕様を読めば分かる — 「ハイブリッド機でも実害なし」と Assumption に VERIFIED で書いたのは、仕様を確認せず自分の期待を書いていた。
- 2026-07-25(セッション11、ユーザー指摘「ブロックを正方形にして本家に近づけると変ですか？意図的でないならデザインして」): 縦長ブロックは誰も決めていない。DESIGN.md には「キャンバスは草の実寸比を維持」と書いてあり、拡張版も OGP も正方形なのに、web 版だけ `DEFAULT_CONFIG` の 960x480 という**先に決まっていた定数**から `computeLayout` が高さを逆算していたため 1:2 に潰れていた。**ルール: 定数(canvas サイズ等)から形を逆算する実装は、仕様に書いた比率を黙って上書きする。「その形はどの数字から出ているか」を実装時に一度たどり、仕様に書いた不変条件(ここでは正方セル)のほうを式の起点にする。**同じ不変条件を 2 箇所以上(core / 拡張 / OGP)が別々に解いていたら、それは core に持ち上げるべき合図。また、**題材の再現度は「らしさ」の装飾より先**に来る — 角丸やアクセント色をいくら足しても、セルが正方形でない限り草グラフには見えない。

- 2026-07-25(セッション8、ユーザー指摘「Slack だと出ない」): 動的 OGP(`/share/{user}`)を作って「OGP 対応済み」と見なしていたが、**実際に一番貼られるトップ URL には OGP タグが1つも無かった**。セッション3 の検証もクローラー UA で `/share/` だけを叩いており、`/` を一度も確認していない。**ルール: OGP/メタ情報は「共有導線で生成される URL」だけでなく、サイトのルートを含む “人が手で貼る URL” 全部について実際に curl して確認する。動的カードを作ったら、静的な既定カードをルートに必ず置く。** 検証は実装したパスではなく、ユーザーが取る行動(URL をコピペする)から逆算して選ぶ。

- 2026-07-25(セッション7、ユーザー指摘「右上の濃い部分残機ですか？みえづらすぎる」): 残機表示をコンテンツと同じ色域(草の緑 level4)で、しかもコンテンツ(草グリッド)の**上に重ねて**描いていたため、草の濃いセルと区別がつかなかった。**ルール: ステータス表示(HUD)はコンテンツの色を借りない。自分で決めた「色に意味を持たせる規則」は UI 全域に適用し、canvas の中も例外にしない。加えて、情報を情報の上に重ねない — 背景が無地の場所に置く。**「初見の人がこれを何だと思うか」を必ず自問する(今回はユーザーが疑問形で尋ねてきた時点で discoverability が失敗している)。対応: 残機=アンバーの「予備のボール」(実際のボールと同色・同径)+ `LIFE` ラベルを、草の直下の無地帯に配置。

- 2026-07-25(セッション5計画、ユーザー指摘): デザインモックのピクセル文字で、未定義グリフ(Z/H/I)を黙って S にフォールバックさせた結果「KUSAKUZUSHI」が「KUSAKUSUSSS」と表示された。**ルール: 文字を描画するデータ(グリフマップ等)は、対象文字列の全文字が定義済みであることを先に検証する。未定義は静かな代替ではなく即エラーにする。** 本実装 demo-grid.ts では「KUSAKUZUSHI の各文字にグリフが存在し、期待どおりのセルパターンが出る」ユニットテストを必須とする(todo.md セッション5 Phase 3 に反映済み)。モックであっても表示内容が仕様(ワードマーク)そのものである以上、手抜きフォールバックは仕様違反になる。
